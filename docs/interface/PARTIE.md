# Premier écran de partie

Le propriétaire a validé le 15 octobre le passage des galeries à un écran utilisable : carte, maison choisie, temps et dossiers simultanés. Les fonctions de carte existantes sont réutilisées ; la simulation reste seule responsable des décisions.
Le travail se livre en deux petites PR : raccordement de la maison (UI-05a), puis écran intégré (UI-06a, avec les commandes de temps existantes). Ce découpage technique ne change pas le résultat attendu : un écran connecté, pas une nouvelle galerie.
`LecturePartie` lit `/monde`, puis `/maison` ou `/departs`. Le choix utilise `POST /intention` avec l’identifiant reçu ; un reçu accepté attend encore la maison dans `/monde`. Aucune maison n’est devinée à partir du choix. En pause, il faut reprendre le temps pour appliquer le choix au prochain tick.
Une seule opération à la fois ; aucun renvoi automatique d’une intention. Une coupure retire les données de maison devenues invérifiables. Un refus conserve son motif. Seuls les identifiants de la liste servie sont proposés.
Preuve UI-05a : quatre nouveaux tests rouges sur le composant vide, puis vingt-deux verts avec UI-01/UI-02 ; [rapports bruts](preuves/partie-tests.zip). Cas : lecture retardée, double choix, refus, identifiant hors liste, coupure et confirmation par le monde. Fixtures explicitement fictives, réservées aux tests.
UI-06a est réalisé sur `direct/interface-ecran` : le cabinet s’installe dans la scène `Forge_Carte`, y compris dans les prochains builds. Il remplace les panneaux de prototype et arrête leur choix direct ; déplacement, zoom et horloge du pont restent utilisés. Le territoire gardé est teinté en rouge, sans changer le monde.

Pour jouer dans Unity 6000.0.43f1 : lancer `py -m sim.service --jours-par-seconde 0` depuis `jeu/`, puis ouvrir **Forge → Interface → Jouer sur la carte** dans le projet `3d/unity` de cette branche. Le service utilise le port 8000. Fermer Play puis arrêter le service avec Ctrl+C.
Choisir une maison, lire son aperçu, confirmer, puis reprendre le temps pour que le monde applique le choix. Glisser/molette parcourent la carte ; un clic droit conserve un territoire à côté de la maison. Après un nouveau build incluant ce code, `pc/Jouer.cmd --carte` lance le service et le jeu ensemble ; un ancien exécutable ne contient pas cet écran.
Preuve du 16 octobre : trois tests d’écran rouges avant implémentation, puis un test supplémentaire rouge sur le choix direct récemment ajouté au pont ; les 26 tests finaux passent. Code éprouvé : `af3d6b28` ; [rapports et manifeste](preuves/cabinet-af3d6b28.zip).
Parcours réel du service local, graine 0 : 596 cellules servies et posées, Bar confirmé par `/monde`, temps repris puis remis en pause, zoom et glissé par événements de souris, territoire 10430 gardé par clic droit ; un clic sur le panneau conserve ce territoire. Aucun nombre de jeu produit par la vue.
[Choix de maison](preuves/cabinet-choix-af3d6b28.png) et [partie en pause](preuves/cabinet-partie-af3d6b28.png) : captures directes de la vue Game, regardées à 1920 × 1080. Papier/encre et accents limités comparés à `imprimerie_1600.png` et `forge_1450.png` ; carte existante conservée.
Limites : police Unity provisoire, disposition éprouvée en 16:9, couleurs et étiquettes de la carte existante, dossier de territoire encore sommaire. Essais dans un projet Unity de contrôle reprenant la scène et le pont du dépôt ; pas de validation du build nocturne complet. Aucun changement de simulation.
